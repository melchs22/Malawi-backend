# Workshop and Service-Centre API

The workshop API is served by the existing Django REST backend under `/api/garages/`. It is independent of roadside-assistance requests under `/api/requests/` and is intended for the separate workshop portal, the Rider/member app, and the admin dashboard.

## Roles and access

| Actor | Access |
|---|---|
| Applicant | Register a service centre and check its application status using its tracking ID. An applicant cannot log in until the service centre is approved. |
| `RIDER` | Browse verified service centres; create and manage their own bookings, respond to quotes, pay their own invoices, and review paid/completed work. |
| `WORKSHOP` | Log in only after admin approval. Access and update only the service centre linked to that owner account. Manage its own booking queue, quotes, and job status. |
| Admin | Users with backend role `ADMIN`, `is_staff`, or `is_superuser` may review service centres, inspect bookings, view audit/review/payment data, and record manual settlements. |

Workshop ownership is enforced on backend querysets and actions, not just in the portal. The public user registration endpoint rejects the `WORKSHOP` role; owner accounts are created by service-centre registration and remain inactive until approval.

## Service-centre application

### Register

`POST /api/garages/register/` — public; rate limited.

The request uses the existing registration fields in `GarageRegistrationSerializer`, including ownership/business details, required exterior/interior photos, offered services and vehicle types, weekly operating hours, and settlement details. Phone numbers are normalized to Malawi E.164 format (`+265...`); local `0`-prefixed numbers are accepted. `operating_hours` uses lowercase weekday keys and `HH:MM-HH:MM` values, for example:

```json
{
  "operating_hours": {
    "monday": "08:00-17:00",
    "tuesday": "08:00-17:00",
    "sunday": "Closed"
  },
  "working_days": ["monday", "tuesday"]
}
```

The response contains only the tracking ID, review status, completeness, and submission date. It does not echo national ID, bank/mobile-money details, or uploaded files.

### Check application status

`GET /api/garages/application-status/?tracking_id=<tracking-id>` — public; rate limited.

Returns the tracking ID, service-centre name, application status, completeness, submission/decision dates, decision reason where applicable, and the approving admin's username when applicable. It does not expose identity documents or settlement details. The tracking ID is generated by the backend.

### Admin review

| Method and path | Purpose |
|---|---|
| `GET /api/garages/admin/` | List applications; optional `status` and `search` query parameters. |
| `POST /api/garages/admin/` | Admin-created service centre. |
| `GET /api/garages/admin/{id}/` | Read application and protected review details. |
| `PATCH /api/garages/admin/{id}/` | Edit application fields; verification and owner assignment are read-only here. |
| `POST /api/garages/admin/{id}/verify/` | Review action: `under_review`, `verify`, `reject`, or `suspend`. Rejection and suspension require a reason. `under_review` disables an already-linked workshop login. |
| `GET /api/garages/admin/{id}/audit/` | Audit history for that service centre. |
| `GET /api/garages/admin/stats/` | Application, booking, invoice, and excess-payment counts. |

On approval, the owner account is activated and a one-time password-setup code is sent to the recorded owner email when the account has no usable password. The owner uses the existing password-reset endpoints with `role: "WORKSHOP"`; password-reset codes expire after 15 minutes. Moving a garage to review, rejecting it, or suspending it disables its linked owner login. Each admin decision and profile change is audited. For a legacy verified garage that has no owner link, an explicit admin `verify` action provisions and activates the owner; no accounts are silently created or enabled by the schema migration.

## Member and workshop appointment lifecycle

1. A member creates a booking at a verified service centre. Requests belong to the authenticated `RIDER`; service and vehicle type must be offered by that service centre. Coordinates are optional but must be supplied as a valid pair when used.
2. The service centre submits an itemized MWK quote and confirms a future working date/time. The API validates the selected day and the centre's published operating hours.
3. The member accepts or declines the quote. Acceptance reserves the confirmed time subject to the service centre's configured mechanic capacity. A quote cannot be edited after acceptance; a new quote revision replaces an unanswered quote.
4. The workshop starts and completes the accepted booking. Completion creates an invoice using the accepted quote total; the quote price is fixed for this release.
5. The member pays the completed invoice using PayChangu. Only a verified provider response with the matching transaction reference, amount, MWK currency, and configured test/live mode marks the invoice paid.
6. Admins record actual workshop transfers manually. Multiple transfer records can be recorded; the final record marks the invoice settled. A final amount below the invoice amount requires an explanation (for example, provider fees).
7. The member may submit one 1–5-star review after the booking is completed and its invoice is paid.

### Member endpoints

| Method and path | Purpose |
|---|---|
| `GET /api/garages/` | List verified service centres and average rating/count (authenticated). |
| `GET /api/garages/{garage_id}/` | Service-centre detail and rating summary. |
| `POST /api/garages/{garage_id}/request/` | Create an authenticated member booking. |
| `GET /api/garages/requests/` | List only the authenticated member's bookings, quotes, invoice, payment status, and review. |
| `POST /api/garages/requests/{id}/quotes/{quote_id}/respond/` | Accept or decline the pending quote; optional `reason`. |
| `POST /api/garages/requests/{id}/cancel/` | Cancel a pending or quoted request. |
| `POST /api/garages/invoices/{invoice_id}/checkout/` | Create or resume the active PayChangu checkout for an owned invoice. |
| `POST /api/garages/payments/{tx_ref}/verify/` | Re-query PayChangu and return verified payment/invoice status. |
| `POST /api/garages/requests/{id}/review/` | Submit one review after paid completion. |

### Workshop portal endpoints

Workshop authentication uses `POST /api/login/workshop/` with the existing username/password login shape. Password setup/reset uses `/api/auth/password-reset/` and `/api/auth/password-reset/confirm/` with `role: "WORKSHOP"`.

| Method and path | Purpose |
|---|---|
| `GET /api/garages/garage/profile/` | Read the authenticated owner's verified profile. |
| `PATCH /api/garages/garage/profile/` | Update approved editable contact, hours, services, pricing, and profile fields. |
| `GET /api/garages/garage/requests/` | List only that owner's bookings; optional `status` and `search`. |
| `GET /api/garages/garage/requests/{id}/` | Read one booking owned by the authenticated service centre. |
| `POST /api/garages/garage/requests/{id}/quote/` | Submit quote `line_items`, `scheduled_date`, and optional `scheduled_time`. |
| `POST /api/garages/garage/requests/{id}/decline/` | Decline a pending booking with a required `reason`. |
| `POST /api/garages/garage/requests/{id}/start/` | Start a member-accepted appointment. |
| `POST /api/garages/garage/requests/{id}/complete/` | Complete in-progress work and issue its invoice. |

Quote example:

```json
{
  "line_items": [
    {"description": "Labour", "quantity": 1, "unit_amount": 20000},
    {"description": "Brake pads", "quantity": 1, "unit_amount": 8500}
  ],
  "scheduled_date": "2026-11-02",
  "scheduled_time": "10:00:00"
}
```

The complete amount must be a positive whole-MWK value within PayChangu's documented API limit. Invalid state transitions return `409 Conflict`; invalid input returns `400`; cross-member/workshop object lookups do not reveal another tenant's record. List endpoints are not paginated in this release.

### Admin operational endpoints

| Method and path | Purpose |
|---|---|
| `GET /api/garages/admin/requests/` | Searchable/filterable platform-wide workshop booking list. |
| `GET /api/garages/admin/reviews/` | Platform-wide workshop reviews. |
| `GET /api/garages/admin/invoices/` | Invoices, payment attempts, and settlement records; optional `status`. |
| `POST /api/garages/admin/invoices/{invoice_id}/settlements/` | Record an external transfer with amount, unique transfer reference, notes, and `is_final`. The transfer is manually verified by operations; this API does not independently confirm the bank/mobile-money transfer. |

## PayChangu configuration and callbacks

The integration follows PayChangu's [Standard Checkout](https://developer.paychangu.com/docs/standard-checkout.md), [transaction verification](https://developer.paychangu.com/docs/transaction-verification.md), and [webhook signature](https://developer.paychangu.com/docs/webhooks.md) requirements.

Configure these server-side environment variables before enabling checkout:

| Variable | Requirement |
|---|---|
| `PAYCHANGU_BASE_URL` | HTTPS API base URL; production default is `https://api.paychangu.com`. |
| `PAYCHANGU_SECRET_KEY` | Merchant API secret key. |
| `PAYCHANGU_WEBHOOK_SECRET` | Webhook signing secret from the PayChangu merchant dashboard. |
| `PAYCHANGU_CALLBACK_URL` | Public HTTPS URL for `/api/garages/payments/callback/`. |
| `PAYCHANGU_RETURN_URL` | Public HTTPS URL in the member app/portal to receive `tx_ref` and `payment_status` after verified checkout. |
| `PAYCHANGU_MODE` | `live` for live credentials or explicitly `test` for PayChangu sandbox credentials. |
| `WORKSHOP_PORTAL_ORIGIN` | The deployed standalone portal origin, added to the backend's explicit CORS allowlist. |
| `TIME_ZONE` | Defaults to `Africa/Blantyre` for the confirmed Malawi release. |

Register `/api/garages/payments/webhook/` in the PayChangu dashboard. The webhook HMAC signature is checked against the exact raw request body, then the backend re-queries PayChangu before changing invoice/payment state. Browser redirects are also server-verified. A missing provider secret, webhook secret, or public HTTPS callback/return URL returns an explicit service error; the backend never fabricates a successful payment or checkout link.

The platform collects payment centrally. No automated split payment or garage payout is implemented. Admin settlement records represent transfers performed outside this API. A second verified successful payment against an already-paid invoice is recorded and flagged as excess for reconciliation; it does not mark the invoice paid twice.

## Roadside and legacy payment compatibility

These APIs are separate from roadside `ServiceRequest` and do not alter its dispatch, status, or real-time route behavior. The existing member wallet/Pesapal flow remains UGX-oriented; this workshop milestone is MWK/PayChangu only. A Malawi-wide migration of existing wallet/roadside payments must be planned separately before claiming every payment path is Malawi-ready.

## Background reconciliation

Celery Beat runs `garages.tasks.reconcile_pending_payments` every 15 minutes. It checks pending sessions at least five minutes old, verifies them with PayChangu, and logs provider failures for retry/operations visibility. The existing webhook and member verification path remain the primary completion signals.
